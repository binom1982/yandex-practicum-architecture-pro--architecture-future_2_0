# Обоснование событийного подхода для «Будущего 2.0»

Документ обосновывает переход от текущей интеграционной архитектуры (ESB на Apache Camel + DWH на MS SQL Server 2008) к событийно-ориентированной архитектуре (Event-Driven Architecture) в горизонте трёх лет.

---

## 1. Текущее состояние: проблемы Camel + DWH

### 1.1. Архитектурные проблемы

| Проблема                                                                                        | Влияние на бизнес                                                                                                                        |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Монолитный DWH** — вся бизнес-логика в одном хранилище | Изменение одного отчёта требует пересборки ETL-процессов, затрагивающих все домены |
| **Синхронные интеграции через Camel**                                    | Отказ одной системы блокирует работу других (каскадные сбои)                                         |
| **Отсутствие границ доменов**                                              | Медицинские данные, финансы, ИИ-сервисы перемешаны в одной модели                                |
| **Пакетная обработка (batch)**                                                   | Отчётность формируется часами, бизнес принимает решения на устаревших данных         |
| **Дублирование бизнес-логики**                                            | Одно и то же правило (например, тарификация) реализовано в разных местах DWH                 |

### 1.2. Организационные проблемы

| Проблема                                                                                                                                     | Влияние на бизнес                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Time-to-market** — запуск нового продукта занимает месяцы                                                 | Компания теряет конкурентное преимущество на рынке финтех-услуг |
| **Зависимость команд** — изменения в одном домене требуют координации со всеми | Аналитики ждут очереди на изменение ETL-процессов                               |
| **Невозможность масштабирования** — DWH не справляется с объёмом данных                | Сотни терабайт данных обрабатываются слишком медленно                   |
| **Нарушение compliance** — медицинские данные смешаны с финансовыми                              | Риск штрафов от регуляторов (152-ФЗ, требования ЦБ)                               |

### 1.3. Технологические проблемы

| Проблема                                                                                                                     | Влияние на бизнес                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MS SQL Server 2008** — устаревшая СУБД, не поддерживает современные паттерны | Невозможно использовать потоковую обработку, нет поддержки JSON, ограниченные возможности масштабирования |
| **PowerBuilder** — устаревший клиентский интерфейс                                               | Сложно найти разработчиков, нет поддержки современных UX-паттернов                                                                          |
| **Apache Camel** — синхронная шина данных                                                                 | Не поддерживает event sourcing, CQRS, реактивные потоки                                                                                                               |
| **Power BI поверх DWH** — жёсткая связь отчётов с физической моделью               | Невозможно построить self-service BI для бизнес-пользователей                                                                                              |

## 2. Целевое состояние: Event-Driven Architecture

### 2.1. Ключевые принципы целевой архитектуры

| Принцип                                        | Реализация                                                                                            |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Доменная изоляция**           | Каждый bounded context имеет свою модель данных и свою БД                     |
| **Асинхронная интеграция** | Домены взаимодействуют через события (Apache Kafka)                            |
| **Event sourcing**                              | Состояние агрегатов восстанавливается из потока событий       |
| **CQRS**                                        | Разделение моделей записи (команды) и чтения (витрины данных) |
| **Реактивные потоки**           | Данные обрабатываются в near-real-time                                                     |
| **Data Mesh**                                   | Каждый домен отвечает за свою витрину данных                              |

### 2.2. Технологический стек

| Компонент                                      | Технология        | Обоснование                                                                                                                                  |
| ------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Event Bus**                                     | Apache Kafka                | Высокая пропускная способность, гарантии доставки, поддержка потоковой обработки |
| **Schema Registry**                               | Confluent Schema Registry   | Централизованное управление контрактами событий, проверка совместимости                |
| **Streaming DW**                                  | ClickHouse + Apache Iceberg | Колоночное хранилище для аналитики, поддержка time-travel                                                       |
| **Self-Service BI**                               | Apache Superset + Trino     | Конструктор отчётов для бизнес-пользователей, SQL-движок поверх витрин                        |
| **Data Catalog**                                  | DataHub                     | Метаданные, lineage, управление доступом                                                                                    |
| **Облачная инфраструктура** | Yandex Cloud / AWS          | Масштабирование, отказоустойчивость, геораспределение                                                  |

## 3. Сравнительный анализ: Camel + DWH vs Event-Driven

| Критерий                               | Текущее (Camel + DWH)                                                       | Целевое (Event-Driven)                                                                                                                      | Выигрыш                              |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| **Time-to-market**                       | Месяцы на запуск нового продукта                       | Дни/недели — новый домен публикует события, подписчики подключаются независимо | **10x быстрее**                |
| **Масштабируемость**     | Вертикальное масштабирование DWH (ограничено) | Горизонтальное масштабирование Kafka-кластера и микросервисов                                   | **Не ограничено**         |
| **Отказоустойчивость** | Каскадные сбои через синхронные вызовы           | Домены изолированы, отказ одного не блокирует другие                                                  | **Высокая**                    |
| **Гибкость**                     | Изменение ETL требует пересборки всей цепочки | Новый подписчик добавляется без изменения издателя                                                    | **Высокая**                    |
| **Скорость аналитики**  | Часы на формирование отчётов (batch)                      | Секунды/минуты (near-real-time)                                                                                                       | **100x быстрее**               |
| **Compliance**                           | Медицинские и финансовые данные в одной БД     | Изоляция доменов, ACL между доменами                                                                                   | **Соответствие 152-ФЗ** |
| **Стоимость владения**  | Высокая (лицензии MS SQL, поддержка legacy)                | Ниже (open-source стек, облачная инфраструктура)                                                                     | **−30% TCO**                         |

## 4. Конкретные выгоды для бизнеса

### 4.1. Для медицинского направления

| Выгода                                                            | Описание                                                                                                                                                                                                                                                |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Быстрый запуск новых сервисов**       | Новый медицинский сервис публикует события `StudyRequested`, `DiagnosisMade` — ИИ-сервисы подписываются и начинают анализ без изменения кода источника |
| **Интеграция с фармацевтами**              | Фармацевтическая компания подписывается на события `PrescriptionCreated` и автоматически формирует предложения пациентам                                             |
| **Масштабирование на новые регионы** | Новый регион — это новый bounded context, который публикует события в общую шину                                                                                                                           |

### 4.2. Для финтех-направления

| Выгода                                                                | Описание                                                                                                                                                                               |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Независимость от медицины**                  | Финтех-домен не зависит от релизов медицинского домена — контракты событий версионируются                        |
| **Быстрый запуск кредитных продуктов** | Новый кредитный продукт — это новый агрегат `CreditAgreement`, который публикует события `CreditApproved`, `CreditDisbursed` |
| **Compliance с ЦБ**                                                | Финтех-домен изолирован, проходит отдельный аудит, использует ACL для интеграции с медициной                       |

### 4.3. Для аналитики и отчётности

| Выгода                                  | Описание                                                                                                                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Self-service BI**                     | Бизнес-аналитик создаёт отчёт в Superset без участия IT — витрины данных доступны через Trino              |
| **Near-real-time отчётность** | KPI рассчитываются на потоковых витринах (ClickHouse + Iceberg), а не на batch-ETL                                                   |
| **Data Mesh**                           | Каждый домен отвечает за свою витрину данных — медицинский домен не зависит от финтех-домена |

### 4.4. Для ИИ-сервисов

| Выгода                                            | Описание                                                                                                                                 |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Потоковая обработка**         | ИИ-модели получают события `StudyRequested` в реальном времени, а не ждут batch-загрузки |
| **Версионирование моделей** | Model Registry управляет версиями моделей, события `ModelPromoted` триггерят обновление      |
| **Масштабирование**                | ИИ-сервисы масштабируются независимо от медицинского домена                                 |

## 5. План перехода (3 этапа)

### Этап 1: Пилот (0–6 месяцев)

| Действие                                                                                                                        | Результат                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Внедрить Kafka в одном-двух доменах (пациентский поток, финансовые расчёты)   | Доказательство концепции, первые события |
| Ввести единые принципы работы с событиями (DLQ, контракты, идемпотентность) | Стандарты для всех доменов                            |
| Развернуть Schema Registry                                                                                                    | Централизованное управление контрактами |
| Запустить пилотную витрину данных (ClickHouse)                                                            | Первые self-service отчёты                                       |

### Этап 2: Масштабирование (6–18 месяцев)

| Действие                                                                                                                          | Результат                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Подключить критические домены (медицинская карта, ИИ-диагностика, биллинг) | Все ключевые процессы на событиях |
| Ввести антикоррупционные слои (ACL) для интеграции с legacy Camel и DWH                         | Плавная миграция без big bang                |
| Запустить потоковые витрины данных                                                                         | Near-real-time аналитика                              |
| Внедрить Data Catalog (DataHub)                                                                                                   | Управление метаданными и lineage         |

### Этап 3: Отказ от legacy (18–36 месяцев)

| Действие                                                                                    | Результат                                                        |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Отказ от синхронных интеграций на критическом пути      | Полная событийная архитектура                  |
| Миграция с MS SQL Server 2008 на облачные хранилища                     | Снижение TCO, повышение масштабируемости |
| Отказ от PowerBuilder в пользу современных UI                              | Улучшение UX для операторов                         |
| Переход к доменной аналитике на основе потоков данных | Полная реализация Data Mesh                               |

## 6. Управление рисками перехода

| Риск                                                                                                             | Вероятность | Влияние | Меры снижения                                                                                            |
| -------------------------------------------------------------------------------------------------------------------- | ---------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Потеря данных при миграции**                                                          | Средняя         | Высокое | Dual-write (параллельная запись в legacy и новую систему), сверка данных |
| **Нарушение compliance при интеграции**                                                  | Низкая           | Высокое | ACL между доменами, аудит потоков данных, шифрование                        |
| **Сопротивление команд переходу на новую архитектуру**            | Средняя         | Среднее | Обучение, пилотные проекты, демонстрация выгод                               |
| **Необходимость поддержки legacy и новой системы одновременно** | Высокая         | Среднее | Поэтапная миграция, чёткие критерии отключения legacy                       |
| **Сложность отладки распределённой системы**                              | Средняя         | Среднее | Централизованное логирование, distributed tracing (Jaeger), мониторинг Kafka    |

## 7. Итоговое обоснование

Переход на событийную архитектуру для «Будущего 2.0» — это **не просто технологическое улучшение**, а **стратегическая необходимость** для:

1. **Масштабирования бизнеса** — выход на новые регионы, запуск новых продуктов (фармацевтика, электроника)
2. **Снижения time-to-market** — с месяцев до дней/недель
3. **Повышения гибкости** — независимое развитие доменов
4. **Обеспечения compliance** — изоляция медицинских и финансовых данных
5. **Снижения TCO** — отказ от дорогих legacy-лицензий (MS SQL Server, PowerBuilder)
6. **Перехода к near-real-time аналитике** — конкурентное преимущество на рынке

Текущая архитектура (Camel + DWH) **не способна** обеспечить эти цели в горизонте трёх лет. Событийная архитектура — это **единственный viable путь** для трансформации «Будущего 2.0» в технологическую компанию.
