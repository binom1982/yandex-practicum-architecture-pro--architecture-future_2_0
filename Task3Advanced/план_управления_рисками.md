# План управления рисками

### 🛠️ Технические меры снижения рисков

| **Риск**                                      | **Мера снижения**                                                                                                                                  | **Как работает**                                                                                                                                                        |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| А1 (нарушение границ)                  | Внедрить Contract Tests и Architectural Fitness Functions                                                                                                   | Автоматические тесты проверяют, что домены общаются только через события.<br />Нарушение → падение CI/CD |
| А2 (некорректная декомпозиция) | Провести Event Storming с бизнесом до начала разработки                                                                           | Совместная сессия выявит реальные границы доменов и агрегатов                                                                      |
| А3 (разные форматы событий)        | Обязательное использование Schema Registry с проверкой совместимости                                                 | Producer не сможет опубликовать событие без зарегистрированной схемы                                                                |
| А4 (потеря консистентности)       | Реализовать Saga Pattern для распределённых транзакций + Outbox Pattern                                                        | Гарантирует, что событие и изменение БД либо оба произойдут, либо нет                                                           |
| А5 (производительность Streaming DW) | Нагрузочное тестирование на реалистичных объёмах (сотни ТБ) с использованием ClickHouse benchmarks | Выявит узкие места до продакшена                                                                                                                             |
| А6 (CDC не справится)                       | Использовать Debezium с шардированием + мониторинг лага репликации                                                 | Алерты при задержке > 5 минут, автоматическое масштабирование                                                                         |
| Т1 (152-ФЗ)                                          | Row-Level Security в Trino + теги классификациив Data Catalog + шифрованиена уровне БД                                        | Медицинские данные физически не попадут в витрину                                                                                             |
| Т2 (требования ЦБ)                         | Аудит всех операцийв ELK + HSM для ключей + георезервирование                                                            | Соответствие 572-П и стандартам ЦБ                                                                                                                             |
| Т3 (зоопарк технологий)               | Стандартизация через Tech Radar (Adopt/Trial/Assess/Hold) + платформенная команда                                             | Чёткие правила выбора технологий, единая экспертиза                                                                                         |
| Т4 (vendor lock-in)                                    | Использование Terraform + Kubernetes (облачно-независимые технологии)                                                       | Возможность миграции между облаками                                                                                                                      |
| Т5 (совместимость версий)           | GitOps + ArgoCDс автоматическим тестированием обновлений в staging                                                            | Обновления проходят через все окружения перед продом                                                                                       |
| Т6 (наблюдаемость)                        | Distributed Tracing (Jaeger/Tempo) + централизованный логинг (Loki) + метрики (Prometheus)                                              | Каждое событие трассируется от источника до потребителя                                                                                 |
| Т7 (безопасность портала)           | WAF + DDoS-защита + OAuth2 + MFA + rate limiting                                                                                                               | Многоуровневая защита API                                                                                                                                            |
| Т8 (потеря данных)                         | Двойная запись в период миграции + автоматическая сверка между Legacy и новой системой            | Расхождения обнаруживаются автоматически                                                                                                           |

### 👥 Управленческие меры снижения рисков

| **Риск**                                         | **Мера снижения**                                                                                                                                                 | **Как работает**                                                                                                                           |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| О1 (сопротивление команд)             | Программа изменений (Change Management): обучение, внутренние хакатоны, «чемпионы» изменений                         | Команда видит выгоды новой архитектуры на реальных примерах                                             |
| О2 (нехватка кадров)                        | Внутренняя академия + найм 2-3 ключевых экспертов + партнёрство с вендорами (Confluent, ClickHouse)                     | Параллельное развитие своих специалистов и привлечение внешних                                      |
| О3 (нет Data Product Owner)                            | Назначить DPO в каждом доменес чёткими KPI (качество данных, time-to-market)                                                            | Ответственность за данные закреплена за конкретным человеком                                          |
| О4 (размывание ответственности)  | RACI-матрица для каждого компонента: кто Responsible, Accountable, Consulted, Informed                                                                | Чёткое разделение: домен отвечает за бизнес-логику, платформа<br />— за инфраструктуру |
| О5 (срыв сроков)                                | Итеративный подход (3 этапа по 6-12 месяцев) + буфер 20% на непредвиденное                                                      | Пилот в одном домене снижает риски масштабирования                                                              |
| О6 (потеря ключевых сотрудников) | Документация legacy-систем + pair programming с новыми сотрудниками + видео-базы знаний                                         | Знания не теряются при уходе одного человека                                                                          |
| О7 (несогласованность)                   | Архитектурный совет (Architecture Review Board) с представителями всех доменов + ежеквартальное планирование | Приоритеты согласованы, конфликты решаются на совете                                                          |

## Дорожная карта управления рисками

### Фаза 1: Первые 6 месяцев (Пилот)

**Фокус:** Снижение критических рисков красной зоны

| **Действие**                                                     | **Ответственный**          | **Результат** |
| ------------------------------------------------------------------------------ | --------------------------------------------- | ---------------------------- |
| Назначить Data Product Owners в пилотных доменах      | CEO + CDO                                     | ✅ О3 снижен          |
| Запустить внутреннюю академию по Kafka/ClickHouse | CTO + HR                                      | ✅ О2 снижен          |
| Внедрить Schema Registry + Contract Tests                              | Platform Team                                 | ✅ А3, А1 снижены   |
| Провести Event Storming с бизнесом                            | Chief Architect                               | ✅ А2 снижен          |
| Задокументировать legacy-системы                       | Legacy Team + новые сотрудники | ✅ О6 снижен          |
| Настроить observability (Jaeger + Prometheus + Loki)                  | Platform Team                                 | ✅ Т6 снижен          |

| Внедрить Saga + Outbox Pattern                                    | Доменные команды      | ✅ А4 снижен          |
| Создать RACI-матрицу для всех компонентов | Chief Architect                      | ✅ О4 снижен          |
| Провести аудит соответствия 152-ФЗ и ЦБ     | Compliance + Security                | ✅ Т1, Т2 снижены   |

### Фаза 3: 18–36 месяцев (Завершение)

**Фокус:** Мониторинг оставшихся рисков + вывод Legacy

| ------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| Автоматическая сверка данных между Legacy и новой системой | Data Engineers                       | ✅ Т8 снижен                       |
| Отключение Legacy DWH и ESB                                                                  | Platform Team                        | ✅ А6 устранён                   |

## KPI управления рисками

**Чтобы измерять эффективность управления рисками, вводим метрики:**

| **Метрика**                                                                           | **Целевое значение** | **Как измеряется** |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------- |
| Количество инцидентов из-за нарушения границ доменов | 0 в квартал                       | Мониторинг Contract Tests   |
| Время обнаружения инцидента (MTTD)                                        | < 5 минут                            | Prometheus + PagerDuty                |
| Время восстановления (MTTR)                                                     | < 30 минут                           | Incident Management                   |
| Задержка CDC                                                                               | < 5 минут                            | Debezium metrics                      |
| Соответствие 152-ФЗ                                                                  | 100%                                      | Аудит Data Catalog               |
| Текучесть ключевых специалистов                                       | < 10% в год                           | HR-метрики                     |
| Time-to-market новой витрины данных                                              | < 2 недели                          | Измеряется в пилоте  |
| Удовлетворённость бизнес-пользователей                         | > 8/10                                    | Опросы аналитиков     |
